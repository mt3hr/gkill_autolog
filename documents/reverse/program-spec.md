# 実装仕様

パッケージの責務とデータの流れをまとめます。
なぜそうしたかは [design-philosophy.md](design-philosophy.md) を参照してください。

## データの流れ

```
[収集]                    [保管]              [整理]           [書き込み]
Windows collect ──┐
Chrome 拡張 ──────┼──→  raw.db  ──→  normalize  ──→  gkill HTTP API
Android アプリ ───┘    (追記専用)      (提案)         (端末別ユーザー)
   └→ JSONL → inbox                                      │
                                                    ledger.db
                                                    (書き込み済み)
```

スクリーンショットと位置情報は別経路です。ファイルとして置くところまでを担当し、
gkill へ入れるのは同期スクリプトの役目です。

## サブコマンド

| コマンド | 何をするか |
| --- | --- |
| `autolog collect` | 常駐して集める。Chrome 拡張の受け口も開く |
| `autolog import` | 生ログを整理して gkill へ取り込む |
| `autolog screenshot` | スクリーンショットを1枚撮る |
| `autolog status` | 生ログの溜まり具合と処理カーソルを表示する |

### フラグ

| コマンド | フラグ | 既定 | 何をするか |
| --- | --- | --- | --- |
| 共通 | `--log` | `info` | ログレベル (debug, info, warn, error) |
| `collect` | `--no-screenshot` | オフ | 定期撮影をしない。タスクスケジューラから `screenshot` を回すとき |
| `collect` | `--screenshot-interval` | 1時間 | 撮影間隔。`AUTOLOG_SCREENSHOT_INTERVAL` より優先する |
| `import` | `--dry-run` | オフ | gkill を呼ばず、書き込む予定だけを表示する |
| `import` | `--until-now` | オフ | 上限を「いま」にする。`--cutoff` とは併用できない |
| `import` | `--cutoff` | 直近の午前4時 | 上限時刻 (RFC3339) |
| `import` | `--since` | 前回のカーソル | 開始位置 (RFC3339) |
| `import` | `--dump-proposals` | なし | 提案を `proposals.jsonl` として書き出すディレクトリ |
| `screenshot` | `--at` | 現在時刻 | 撮影時刻として記録する日時 (`2006-01-02T15:04:05`) |
| `status` | `--since` | `24h` | 集計開始位置。期間 (`24h`, `7d`) か RFC3339 の時刻 |
| `status` | `--dump` | オフ | 件数だけでなくイベントの中身も表示する |

### autolog import の流れ

1. 共有ディレクトリの JSONL を生ログへ取り込む（Android のみ。`inbox`）
2. 処理カーソル 〜 上限時刻の生ログを読む
   （低水位マークがカーソルより過去を指していれば、そこまで遡る。次項）
3. `normalize` で提案を作る
4. 台帳にある提案を除く
5. 端末ごとに gkill へログインして書き込む
6. 書き込めた分を台帳へ記録する
7. 持ち越し（開区間・通知の既読）を保存し、処理カーソルを進める
   （失敗した提案の手前まで引き戻す）。読み終えた低水位マークを消す

`--dry-run` を付けると 5〜7 を行いません。受け口の JSONL も消しません。

処理カーソルがまだ無いとき（初回）の開始位置は**7日前**です。
`--since` を付ければ好きな位置から読み直せますが、台帳が効くので
既に書き込んだ分が増えることはありません。

### 遅れて届いた生ログは低水位マークで読み直す

区間イベントは**終わってから**届きます。取り込みの時点で開いていた区間
（使用中のアプリ、再生中の音楽、Chrome 拡張が溜めていた閲覧）は、
次の書き出しで届いたときにはカーソルより過去の `start_time` を持っています。
カーソルから先だけを読んでいると、この分が二度と取り込まれません。

そこで `raw.db` への挿入時に「カーソルより過去のイベントが入った」ことを
低水位マーク（`process_cursor` の `backfill` 行）として同じトランザクションで残し、
次の取り込みはマークまで遡って読み直します。読み直しの重複は台帳の
イベント包含（後述）が防ぎます。読み終えたマークは消しますが、
取り込み中に新しい遅着があれば値が変わっているので消えず、次回へ引き継がれます。

遅着イベントが**確定済みの区間を延ばす**形になった場合
（結合幅の内側に届いた場合）は、既に書いた短い区間と重なる長い区間を
もう1本書くことになるため、区間系の TimeIs（ウィンドウ・アプリ利用、
メディア再生、端末利用）では書き込みません（`重なりで除外` として表示）。
延びた分の記録は失われますが、重複した TimeIs を作るよりましという判断です。

### 取り込みは同時に1つしか動かない

開始時に `$AUTOLOG_HOME/import.lock` の OS ファイルロックを取り、
取れなければ何もせずに失敗します（`internal/proclock`）。

台帳の既書き込み判定は起動時のスナップショットで、Kyou の ID は書き込みごとに
採番されます。並行して走ると両方が「未書き込み」と判定し、同じ区間の Kyou が
二重に登録されるためです。午前4時のタスクと手動実行・同期スクリプト経由の
実行は現実に重なります（URLog は1秒に1件しか書かないので、1回の取り込みは
数分かかることがあります）。

ロックはプロセスが死ねば OS が解放します。ロックファイルが残っていても
次の起動を妨げないので、消す必要はありません。

## internal/collect — Windows での収集

`autolog collect` から4つのゴルーチンが動きます。
書き出し役 (`emitter`)、前面ウィンドウ、セッション、ネットワーク・電源です。

Windows 以外では「収集しない」実装になります (`run_other.go`)。

### 収集も同時に1つしか動かない

開始時に `$AUTOLOG_HOME/collect.lock` の OS ファイルロックを取り、
取れなければ **raw.db に触る前に**失敗します（`internal/proclock`）。

これが無いと、常駐中に手でもう1つ起動したとき、2個目が
稼働中インスタンスの開きっぱなしセッションを「前回の異常終了」と誤認して
偽の recovered lock を書き、collector_start / collector_stop も書いてから
受け口のポート衝突で死にます。利用セッションが分断され、
接続区間も観測の切れ目として閉じられてしまいます。
ポートの衝突は「書いたあと」に起きるので、排他の代わりにはなりません。

### 見張る間隔

| 対象 | 間隔 | 何をするか |
| --- | --- | --- |
| 入力 | 1秒 | その1秒に入力があったときだけ前面ウィンドウを読む |
| 同じウィンドウ | 30秒 | 触り続けている間、30秒ごとに記録し直す |
| Wi-Fi・Bluetooth・充電 | 15秒 | 前回と変わったときだけイベントにする |

入力が無い秒は前面ウィンドウを読みません。マウス移動は入力に数えません。

**アイドル判定はここでは行いません。** 5分無入力でセッションを切るのは
`normalize` の役目です。収集は「いつ触ったか」を残すだけにしてあります。

### 書き出しはまとめるが、セッションだけは即時

5秒ごと、または64件たまった時点でまとめて `raw.db` へ書きます。
ただし `session` のイベントだけは、たまるのを待たずその場で書きます。
ロックやシャットダウンでは直後にプロセスが止まるため、
待っていると記録そのものが失われるからです。

キューは1024件で、あふれたら捨てます。書けないまま溜め込んで
収集全体を止めるより、その分を落とすほうがましだからです。

### 異常終了したセッションを閉じる

収集が落ちるとセッションが開きっぱなしになります。次の起動時に
最後のセッションイベントを見て、それが開始側だったら閉じるイベントを足します。

終了時刻は**最後に入力があった時刻**（無ければそのセッションの開始時刻）です。
イベントIDは `recovered-<時刻>` という決まった形にしてあるので、
何度起動し直しても増えません。

## internal/winapi — Win32 API のラッパ

cgo を使わず `golang.org/x/sys/windows` の LazyDLL で呼びます。
中身は全部 `_windows.go` にあるので、他のプラットフォームからは空のパッケージに見えます。

踏んだ問題がそのまま実装の理由になっています。

- **Bluetooth の接続判定に `fConnected` を使わない。** BLE を取りこぼすうえ、
  値が古いままのことがあります。SetupAPI でデバイスのプロパティを見ます
- **充電は AC につながっているかで見る。** バッテリー側の充電ビットで判定すると、
  満充電になった時点で落ちて TimeIs が細切れになります。残量と充電方式は読みません
- **Wi-Fi の SSID には位置情報の許可が要る。** 無いと `ERROR_ACCESS_DENIED` に
  なるので、一度だけ警告を出して空として扱います。BSSID は読みません
- **ロック判定は `OpenInputDesktop` が失敗するかどうか。** セッションの開始・終了
  そのものはウィンドウメッセージで受け取ります
- **コンソールは、自分だけがぶら下がっているときしか隠しません。**
  端末から手で起動したときに消えると困るためです

## internal/shot — スクリーンショット

### 撮る時刻は「間隔で割った境目」

「間隔ぶん経ったら撮る」ではありません。1時間なら毎時00分、
15分なら毎時00分・15分・30分・45分になります。

`NextTick` / `RoundToTick` は `time.Truncate` を使うので、UTC の基準時刻からの
絶対時間で丸まります。壁時計の切りの良い時刻に揃うのは、1時間を割り切る間隔か、
時間単位の間隔で、かつ UTC との差が時間単位の地域（JST は該当）に限られます。

PC 側は `AUTOLOG_SCREENSHOT_INTERVAL`（`autolog collect --screenshot-interval` が優先）、
Android 側はアプリの設定画面で決めます。Android は `config.env` を見ません。
撮影するのは収集アプリで、Termux の `autolog` は撮らないためです。

### 撮って置くだけ

全モニターを1回の `BitBlt` で1枚に収めます。モニターの配置が長方形にならない
場合、隙間は黒のままです。WebP は可逆で、画質の設定はありません。

ファイル名は `<端末名>_YYYY-MM-DD_HH-mm-ss.webp`。秒まで入っているので、
1時間未満の間隔でも衝突しません。置き場は日付で分けずフラットです。

**`.tmp` へ書いてから rename します。** `gkill_server idf` が
書きかけのファイルを拾わないようにするためです。
既にあるファイルは上書きしません。ここが崩れると撮り逃しになります。

ロック中は撮りません。撮り逃した時間の画像を後から作ることもしません。

### 保存後に更新時刻を撮影時刻へ合わせる

gkill の IDF は更新時刻を記録時刻として使うためです。
これをしないと、取り込んだ日時で記録されてしまいます。

## internal/rawlog — 生ログ

SQLite。生ログ本体は追記専用です。

```sql
CREATE TABLE raw_event (
  schema_version INTEGER NOT NULL,
  event_id       TEXT NOT NULL,   -- 端末内で一意
  device         TEXT NOT NULL,
  event_type     TEXT NOT NULL,
  start_time     TEXT NOT NULL,   -- RFC3339
  end_time       TEXT,
  captured_at    TEXT NOT NULL,
  payload        TEXT NOT NULL    -- JSON。加工前の値
);
CREATE UNIQUE INDEX idx_raw_event_id ON raw_event(device, event_id);
CREATE INDEX idx_raw_event_start ON raw_event(start_time);
CREATE INDEX idx_raw_event_type_start ON raw_event(event_type, start_time);
```

処理の途中状態を持つテーブルが3つあります。どれも生ログではないので上書きします。

```sql
-- どこまで処理したか
CREATE TABLE process_cursor (
  name       TEXT NOT NULL PRIMARY KEY,
  value      TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

-- まだ終わりが決まっていない区間。次回へ持ち越す
CREATE TABLE open_state_interval (
  device     TEXT NOT NULL,
  source     TEXT NOT NULL,
  state_key  TEXT NOT NULL,   -- SSID・機器名・アプリ名・再生の識別子
  title      TEXT NOT NULL,
  start_time TEXT NOT NULL,
  end_time   TEXT,            -- NULL なら切断をまだ観測していない
  event_ids  TEXT NOT NULL,   -- JSON 配列
  PRIMARY KEY (device, source, state_key)
);

-- 短時間の同内容再通知を、バッチをまたいで1件にまとめるための既読記録
CREATE TABLE notification_seen (
  device       TEXT NOT NULL,
  content_hash TEXT NOT NULL,
  last_at      TEXT NOT NULL,
  PRIMARY KEY (device, content_hash)
);
```

`end_time` は後から足した列です（`CREATE TABLE IF NOT EXISTS` は既にある表を
作り替えないので、列の追加はマイグレーションで行います）。使い分けは2通りです。

- **接続状態（Wi-Fi・Bluetooth・充電）は NULL のまま。** まだ切断を観測していない、
  つまり終わりが本当に分かっていない区間です
- **アプリ利用とメディア再生は暫定の終了時刻を持つ。** 終わりは観測できていますが、
  結合の窓の中にいるのでもっと延びるかもしれない区間です

`notification_seen` は上限時刻から重複排除の窓のぶんだけ遡った時刻より
古い行を落としてから書き直します。溜め続けても使わないためです。

### 時刻は必ずローカルへ揃えてから保存する

`storageTime()` が保存直前に `time.Local` へ変換します。

時刻を文字列で持ち `ORDER BY start_time` で並べるため、
オフセットが混ざると辞書順が時刻順と一致しなくなります。
Chrome 拡張や Android は UTC (末尾 Z) で送ってくることがあるので、
入口ではなく保存の直前で揃えます。

### イベントの種類

| event_type | 内容 |
| --- | --- |
| `input` | クリック・ホイール・キー入力を伴う前面ウィンドウ。マウス移動では出さない |
| `session` | 端末の利用状態の変化。`action` は `logon` `unlock` `resume` `collector_start`（開始側）と `lock` `logoff` `shutdown` `suspend` `screen_off` `collector_stop`（終了側） |
| `wifi` | Wi-Fi の接続・切断。SSID のみ。BSSID は持たない |
| `bluetooth` | Bluetooth 機器の接続・切断 |
| `power` | 充電の開始・終了。残量は持たない |
| `browser_view` | ブラウザでのページ表示 |
| `media_play` | 動画・音楽の再生（実再生時間つき） |
| `app_usage` | アプリの利用 |
| `notification` | 通知 |

## internal/normalize — 整理

生ログを提案へ変換します。**ここが本システムの中核**です。

外部に依存しない純粋な処理なので、入力を並べれば結果が決まります。
境界値の単体テストを厚く書いてあります。

### 閾値

要件で決めた値です。根拠は [requirements.md](requirements.md) にあります。

| 定数 | 値 | 用途 |
| --- | --- | --- |
| `IdleTimeout` | 5分 | これだけ入力が無ければウィンドウのセッションを終える |
| `WindowMergeWindow` | 1分 | この時間内に元のウィンドウへ戻ったら前後を結合する |
| `MinWindowDuration` | 1分 | これ未満のウィンドウ操作は記録しない |
| `MinViewDuration` | 30秒 | これ未満の閲覧は記録しない |
| `MinPlayedSeconds` | 30秒 | これ未満しか再生していないものは記録しない |
| `MinAppUsage` | 1分 | これ未満のアプリ利用は記録しない。PC 側の `MinWindowDuration` と揃えてある |
| `WifiMergeWindow` | 30秒 | この時間内の再接続を結合する |
| `BluetoothMergeWindow` | 1分 | 同上 |
| `ChargeMergeWindow` | 30秒 | 同上 |
| `NotificationDedupeWindow` | 5分 | この時間内の同内容の再通知を1件にまとめる |

### セッションの終わりは「最後の入力時刻」

5分無入力でセッションを終えますが、終了時刻は**アイドルと判定した時刻ではなく
最後に入力があった時刻**です。触っていない5分間を記録に含めません。

### 継続中のセッションは持ち越す

上限時刻の時点でまだ終わっていないものは提案にしません。次回まとめて処理します。

持ち越し方は2通りあり、対象によって使い分けます。

**ウィンドウ操作と端末利用**は、処理カーソルをその開始時刻まで引き戻します。
開いているのは常に「いま操作中の1件」なので、引き戻す幅は高々直近の数分です。
カーソルを引き戻せるのはこの2つだけで、他はすべて下の方式です。

**接続状態（Wi-Fi・Bluetooth・充電）とアプリ利用・メディア再生**は、
カーソルを引き戻さず、区間そのものを `raw.db` の `open_state_interval` へ
保存して次回へ渡します。

接続状態を引き戻し方式にできないのは、**切断しない機器があると永久に止まるから**です。
スマートウォッチのように常時つないだままの機器があると区間が閉じることはなく、
カーソルはその接続時刻に固定され続けます。処理する生ログは日ごとに増え、
いずれ現実的な時間で終わらなくなります。

アプリ利用とメディア再生は、終わりは観測できていますが、結合の窓（1分）の中に
いる末尾はまだ延びるかもしれません。そのまま出すとバッチの切れ目で区間が割れるので、
暫定の終了時刻つきで持ち越し、次回に続きが来れば結合します。

持ち越した区間は次回の区間組み立ての起点として使うので、
**開始イベントが処理範囲の外に出ていても正しく閉じられます**。

### 通知の重複排除もバッチをまたぐ

同じ内容の再通知を5分以内なら1件にまとめますが、その「前に記録した時刻」を
`notification_seen` に持ち越します。これが無いと、バッチの切れ目をまたいだ
再通知だけが重複して残ります。

記録した通知だけが既読を更新します。除外された通知では更新しません。

### 提案の ID は決定的

`makeID(種別, 収集元, 元イベントID群)` を sha256 で計算します。
同じ生ログからは常に同じ ID が出るので、台帳での重複判定に使えます。

### 再生は TimeIs、URL があれば URLog も

再生していた区間は常に TimeIs にします。URL を確定できた再生には、それに加えて
URLog も作ります。区間と「何を再生したか」は別の事実だからです。

TimeIs は同じコンテンツの再生が1分以内に続いていれば1本にまとめるので、
TimeIs 1本に対して URLog が複数並ぶことがあります。
`makeID` は種別を含めて計算するので、同じイベントから2つ作ってもIDは衝突しません。

**同じコンテンツかどうかは 動画ID → URL → タイトル の順で判定します。**
タイトルだけで判定してはいけません。自動再生で次へ進む間隔は数秒しか空かないので、
題名がたまたま同じだと別のコンテンツどうしが1本にまとまってしまいます。

### 動画・音楽はブラウザ経路から除く

同じページが閲覧区間としても届くため、そのままだと同じ URL の URLog が2件になります。
`mediaPlays` を `browserViews` より先に走らせ、再生として URLog にした URL は
閲覧側で落とします。

YouTube・YouTube Music はホスト単位でブラウザ経路から除きます。
閲覧 URL には `&list=` などが付いて再生 URL と一致せず、
トップページや検索結果まで URLog になってしまうためです。
判定はホスト名で行います（URL に文字列が含まれるかで判定すると誤爆します）。

### Bluetooth 機器名の先頭の `LE_` を落とす

1台の機器がクラシックと Low Energy の両方でつながると、Android は
`Headphones` と `LE_Headphones` という別々の名前で通知してきます。
そのままだと同じ機器の TimeIs が2本並び、2台つけているように見えます。

接頭辞を落として同じキーにすれば、区間の組み立てが「既に接続中」として吸収します。
落とすのは**先頭にあるときだけ**です。`LED Lamp` のような名前や、
途中に `LE_` を含む名前は変えません。

## internal/gkillclient — gkill への書き込み

純 Go の `net/http` だけを使います。

| 用途 | エンドポイント |
| --- | --- |
| ログイン | `POST /api/login` |
| TimeIs | `POST /api/add_timeis` |
| URLog | `POST /api/add_urlog` |
| Kmemo | `POST /api/add_kmemo` |
| タグ | `POST /api/add_tag` |

### 応答は必ず中身を見る

gkill は異常時も HTTP 200 を返し、本文の `errors` にエラーを載せます。
ステータスコードだけを見ていると失敗を見落とします。

### 端末名は自分で設定する

エンティティを丸ごと送るので、`create_app` に `gkill_autolog`、
`create_device` に端末名が入ります。

`rep_name` は送っても無視されます（追加ユースケースが書き込み用リポジトリ固定のため）。
書き分けは端末別ユーザーで行います。

### ログインの失敗は繰り返さない

一度失敗したら、その実行中はもう試みません。
gkill のログインは IP ごとに 15 分で 10 回までなので、
提案ごとに再試行すると上限を使い潰して復帰を遅らせます。

書けなかった分は台帳に載らないので、次回やり直されます。

### URLog は1秒に1件

gkill が `add_urlog` のたびに対象 URL を取得しに行くためです。
タイトルは必ず自分で埋めて送ります。

## internal/ledger — 書き込み済み台帳

`ledger.db` に「この提案はもう書き込んだ」と「その元イベント」を持ちます。

```sql
CREATE TABLE written (
  proposal_id TEXT NOT NULL PRIMARY KEY,
  kind        TEXT NOT NULL,   -- timeis / urlog / kmemo
  kyou_id     TEXT NOT NULL,
  written_at  TEXT NOT NULL
);

CREATE TABLE written_event (
  kind        TEXT NOT NULL,
  source      TEXT NOT NULL,
  device      TEXT NOT NULL,
  event_id    TEXT NOT NULL,
  proposal_id TEXT NOT NULL,
  PRIMARY KEY (kind, source, device, event_id)
);
```

**書き込みに成功した分だけ**記録します。失敗した分は載らないので次回やり直されます。
提案の ID は生ログから決定的に計算できるので、作り直しても同じ値になり、
重複判定に使えます。

提案 ID だけでは足りません。カーソルの引き戻し（継続中セッションや書き込み失敗、
低水位マーク）で確定済み区間のイベント列を途中から読み直すと、部分集合の
イベントから**別の ID** を持つ提案が再構成されます。`written_event` で
元イベントを突き合わせ、「元イベントがすべて記録済み」の提案は
既に書いた区間の断片とみなして弾きます。

一部だけが記録済みの提案（遅着イベントが確定済み区間を延ばした形）の扱いは
収集元で分かれます。区間系の TimeIs（ウィンドウ・メディア・端末利用）は
書くと同じ時間帯の TimeIs が2本になるので弾きます。接続系は観測の切れ目
マーカーを複数の区間が共有するため、通知は同じ通知の更新列が正当に重なるため、
どちらも一部重複のまま通します。判断は台帳ではなく書き込み側にあります。

タグ付けが失敗しても、本体が書けていれば台帳には載ります。
そのため**既に書き込んだ Kyou に後からタグは付きません**。

## internal/inbox — Android からの受け渡し

共有ディレクトリの `*.jsonl` を読んで生ログへ入れます。

- `.jsonl` だけを読みます。書きかけの `.jsonl.tmp` は読みません
- 取り込めたファイルは消します。消す前に落ちても、生ログ側が重複を弾くので壊れません
- 1行が壊れていても、他の行は取り込みます
- 端末名が許可されていなければその行だけ捨てます
- 受け付けなかった行があるファイルは**消しません**。生ログを恒久に失わないためで、
  原因（端末名の設定やスキーマ）を直せば次回の取り込みで残りが入り、そのとき消えます

## internal/ingest — Chrome 拡張の受け口

`POST /ingest` のみ。既定では 127.0.0.1 だけに bind します
（`AUTOLOG_INGEST_ADDR` で変えられますが、127.0.0.1 のままにすること）。
`Authorization: Bearer <token>` を要求します。

トークンは初回起動時に生成して `$AUTOLOG_HOME/ingest_token.txt` に保存します。

端末をまたぐ受け口は持ちません。

## internal/config — 設定

優先順位は次のとおりです。

1. 環境変数
2. `$AUTOLOG_HOME/config.env`
3. 共有ディレクトリの `config.env`（Android のみ）
4. 既定値

設定ファイルは KEY=VALUE 形式です。`#` で始まる行と空行は無視します。
先頭の BOM は取り除きます。

### 環境変数からしか設定できないもの

`AUTOLOG_SHARED_DIR`（収集アプリとの受け渡しに使うディレクトリ）だけは
`config.env` に書けません。**そこに置かれた `config.env` を読むために、
設定ファイルより先に決まっている必要がある**ためです。

Android では省略時に `/sdcard/gkill_autolog` になります。
Android 以外では空で、受け渡しそのものを行いません。

`AUTOLOG_HOME` も同じ理由で、実質的に環境変数だけで決まります。

### 端末名の既定値

未設定ならこの機械のホスト名を使います。
端末名に使えない文字（アンダースコア、空白、ドット）は落とします。

コードに端末名は書きません。

### タイムゾーン (Android)

`timezone_android.go` がシステム設定からタイムゾーンを読み、`time.Local` に入れます。
`main()` の先頭で、他の処理より先に実行します。

Android 以外では何もしません。

## Android アプリ

### 端末名は config.env が優先

アプリの設定と `config.env` の両方に端末名を持つと食い違います。
`config.env` を正とし、起動時にアプリの設定へ反映します。

### 書き出しは排他する

常駐サービスが1時間おき、WorkManager が15分おき（Android の最短周期）に呼ぶため、
プロセス内で排他します。これが無いと、同じ内容の JSONL が二重に書き出されます。

書き出したファイルは `<端末名>-<時刻>.jsonl.tmp` へ書いてから `.jsonl` へ名前を変えます。
書けた分だけをアプリ内の DB から消すので、書けなければ端末に残って次回やり直されます。

### 外から書き出しをさせられる

`ExportReceiver` を明示的に叩くと、その場で書き出します。
Android 側の取り込みスクリプトが取り込みの直前に使います。これが無いと、
アプリ内に溜まっている直近の記録が共有ディレクトリに出ないまま取り込みが走ります。

```sh
am broadcast --user 0 -f 0x20 -n com.mt3hr.gkill_autolog/.ExportReceiver
```

`am broadcast` は順序付きブロードキャストを送って完了まで待ち、受け口は
`goAsync()` で書き出しが終わるまで完了扱いにしないので、**呼び出し側は完了を待てます**。
結果コードに件数、結果データに人が読める文字列を載せるので、成否を判別できます。

`intent-filter` は付けません。呼ぶ側にコンポーネント名を明示させることで、
他のアプリのブロードキャストにたまたま反応することがなくなります。

### 更新後も収集を続ける

Android はアプリを入れ替えるとプロセスを停止しますが、常駐サービスは自動では戻りません。
`BootReceiver` は端末起動時の `BOOT_COMPLETED` に加えて、
更新完了時に自分自身へだけ届く `MY_PACKAGE_REPLACED` でも収集を開始します。

これが無いと、更新のたびに収集が黙って止まり、
設定画面で「収集を開始」を押すまで記録が途切れます。

### 直前の SSID は永続化する

Wi-Fi の切断時は SSID を取得できないため、直前に接続していた SSID を覚えておいて
切断イベントを作ります。この値はメモリだけで持たず永続化します。

プロセスが死ぬと失われ、復帰後は切断イベントを作れなくなります。
すると接続区間が閉じないまま残り、
[持ち越し開区間](glossary.md#持ち越し開区間-open_state_interval) に溜まり続けます。

### 位置情報 (GPX)

`LocationCollector` が `LocationManager` で GPS とネットワークの両方を購読します。
`FusedLocationProviderClient` は使いません。Google Play 開発者サービスへの
依存を増やさないためです。Android 12 以降にある `LocationManager.FUSED_PROVIDER` は
OS 側の融合測位で Play 開発者サービスとは関係が無いので、使える端末では併せて購読します。

屋内では GPS が入らずネットワーク側しか取れないことがあるので両方を購読します。

**記録間隔ごとの窓に対して、その窓でいちばん精度の良い点だけを残します。**
以前は先に届いた点をそのまま採り、あとから来た点を時刻だけで捨てていました。
精度を比べていなかったので、屋内では誤差 1km 級のセル測位が、
数秒後に届く誤差 10m の GPS 測位に勝ってしまい、経路が大きく飛んでいました。

点を採る前に2つ捨てます。

* **設定した許容誤差より粗い点**（既定 100m）。取れなかった時間は点を置かないままにします。
  分からないものを埋めないためです
* **古い点。** 購読を始めた直後は、以前に測った位置がそのまま流れてきます。
  `elapsedRealtimeNanos` で測って1分より古いものは、いま居る場所ではないので捨てます

精度が取れなかった点は捨てません。順位はいちばん下に置き、
ほかに点が無ければ記録します。観測できた事実は残すためです。

**高精度モード**（既定オン）では、記録間隔より短い周期（5秒）で測位して
窓の中の候補を増やします。オフにすると測位の回数は記録間隔どおりに戻ります。
どちらでも「いちばん精度の良い点を残す」動きは変わりません。
オフでも GPS・ネットワーク・FUSED の2〜3点から選べます。

点は `GpsPointStore`（アプリ専用領域の SQLite）に貯めます。
メモリだけで持たないのは、プロセスが落ちたときにその日のそれまでの分を失わないためです。
窓の中でいちばん良い点を選ぶのも、メモリに溜めてから決めるのではなく
`putBest` がその場で DB を更新します。途中で落ちてもそこまでの点が残り、
あとから精度の良い点が来れば置き換わります。

**この DB を作り直す移行をしてはいけません。** `GpxWriter` はその日の GPX を
DB の全点から毎回作り直すので、点を消すと次の書き出しで、
書き出し済みの当日分の軌跡が短くなって消えます。列の追加で移行します。

`GpxWriter` が1分おきに、点が入っている日をすべて書き出します。
当日だけでなく過去日も対象にするのは、日付が変わった直後に前日分を書き残さないためです。

**その日の全点から毎回作り直し、`.tmp` へ書いてから rename します。**
追記にしないのは、GPX に閉じタグが要るからです。書きかけのファイルを
同期スクリプトがコピーすると解釈に失敗し、その rep の GPS ログ全体が読めなくなります。

書いた点は7日残してから消します。書き損じても作り直せるようにするためです。

### 撮り逃したときの撮り直し

撮る時刻の決め方とファイル名は PC 側と同じです（`internal/shot` の節）。
違うのは、撮り逃したぶんを次に画面が点いたときに撮ることだけです。

区切りの時刻に画面が消えていると撮れません。Windows は据え置きの機械なので
これで困りませんが、スマホは大半の時間で画面が消えているため、
区切りちょうどを待っているとほとんど撮れません。tick は5秒間隔なので、
「区切りの5秒以内に画面が点いている」必要があるからです。

そのため `ScreenshotCollector` は、撮れなかった区切りを `pendingBucket` として覚え、
次に画面が点いた時点で撮ります。

**このとき記録する時刻は実際に撮れた時刻です。** 区切りの時刻を名乗らせると、
撮れていない時間の画像をでっち上げることになります。記録時刻がずれるのは
「その時刻に観測できた」という事実そのものなので、こちらが正しい形です。

借りとして持つのは最後の1区切りだけです。何時間も消えていたあとに、
その間の回数ぶんをまとめて撮っても意味がありません。

ロック中も撮りません。ロック画面には中身が無く、Windows 側が
`IsSessionLocked` で撮らないのと揃えています。

root の `screencap` を使います。root が無い端末では撮れません。
MediaProjection は起動のたびに確認ダイアログが出るので使いません。

保存後に更新時刻を撮影時刻へ合わせるのは PC 側と同じです。
