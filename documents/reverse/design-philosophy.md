# 設計思想

なぜこの形になったのか、何を避けたのかを記録します。
実装の詳細は [program-spec.md](program-spec.md) を参照してください。

## 全体を貫く方針

### 記録するのは観測できた事実だけ

目的・感情・集中状態は推測しません。要約もしません。
「何のためにこのウィンドウを開いていたか」は分からないので書きません。

取れなかった情報は補完しません。動画のタイトルが取れなければ、
URL を推測して記録するのではなく、その1件を諦めます。

### 判断は決定的なルールで行う

何を残すかは、閾値と除外リストだけで決まります。
同じ生ログからは、何度実行しても同じ結果が出ます。

当初は LLM に URL の取捨を判定させる設計でしたが、やめました。

- 日々数千件のイベントを流すとコストが大きく、出力が揺らぐ
- ルール処理なら境界値の単体テストが書けて、再現性を担保できる
- 判定役が落ちても取り込みが止まらない

いま残っているのは `url_denylist.txt` と `notification_denylist.txt` の2枚だけです。
どちらも利用者が読んで直せます。

### 生ログは消さない

観測した事実は追記専用の SQLite に貯め、削除しません。
取り込みの規則を変えたときに、過去へ遡って作り直せるようにするためです。

`(端末名, event_id)` で一意にしてあるので、同じイベントを二度入れても増えません。
再送・再取り込み・障害からの復帰が、特別な手当てなしに安全になります。

### 失敗しても次回やり直せる形にする

書き込めた分だけを台帳に記録し、処理カーソルは失敗した提案の手前まで引き戻します。
途中で落ちても、次の実行が残りを拾います。

そのため「失敗＝そこで止める」ではなく「失敗＝記録せず次へ」を基本にしています。

## 端末内で完結させる

各端末が自分で集め、自分の gkill へ取り込みます。端末をまたぐ転送はしません。

以前は Android が生ログを PC へ HTTP で送る設計でしたが、
片方が落ちていると溜まり続けるうえ、受け口の認証と端末識別が余計に必要でした。

いまは各端末が自分の gkill に書き、そこから先は gkill 側の同期の仕組みに任せます。
autolog は取り込みまでを担当し、集約には関与しません。

## gkill への書き込みは HTTP API を直接叩く

当初は gkill の Write MCP サーバ (Node) を子プロセスで起動し、
stdio の JSON-RPC で会話していました。これをやめて HTTP API を直接叩いています。

理由は3つあります。

**Android で Node を動かせない。** 端末内で完結させる以上、Node 依存は捨てるしかありません。

**MCP は端末名を書けない。** MCP は `create_app` を `gkill_mcp_write`、
`create_device` を `mcp` に固定します。どの端末で記録したかが Kyou に残らないため、
やむなく端末名のタグで代替していました。
HTTP API はエンティティを丸ごと受け取るので、これらを自分で設定できます。
いまは `create_app` に `gkill_autolog`、`create_device` に端末名が入り、
端末タグは不要になりました。

**層が1つ余分だった。** MCP の実体は gkill の HTTP API を叩いているだけです。

## 書き込み先リポジトリは指定できない

gkill の追加 API は、リクエストに `rep_name` を載せても無視します。
すべての追加ユースケースが書き込み用リポジトリ固定で動くためです
（`usecase/timeis.go` の `WriteTimeIsRep` など）。

そのため、端末ごとに別のファイルへ書き分けるには**ユーザーを分ける**しかありません。
`<接頭辞><端末名>` というユーザーを端末ごとに用意し、それぞれの既定の場所へ書きます。

そこから先へ運ぶのは gkill 側の同期スクリプトの役目です。
アカウント名から端末名を取り出し、`Auto<種別>_<端末名>_<日付>.db` として運びます。

## URLog はサーバに負荷をかける

gkill は `add_urlog` のたびに、対象の URL をサーバから取得しに行きます
（`handle_add_urlog.go` → `FillURLogField` → `getBody`）。
favicon が空なら外部サービスへも取りに行きます。

数百件をまとめて書くと、同じ数の外向き通信がサーバから出ます。
社内ページや認証が要るページにも及びます。

そのため URLog は**1秒に1件**に抑え、タイトルは必ず自分で埋めて送ります
（空にするとサーバが取得結果から埋めようとするため）。
説明文とサムネイルの充填は諦めています。クライアントから抑止する手段がありません。

## ログインは数えられている

gkill のログインは **IP ごとに 15 分で 10 回**までです
（`gkill_server_api_rate_limit.go`）。ユーザー単位ではありません。

一度ログインに失敗したら、その実行中はもう試しません。
提案ごとに再ログインすると、上限をさらに使い潰して復帰を遅らせるだけだからです。

実際、確認スクリプトを数回叩いた直後に取り込みを走らせて、
2台目の端末の分が全滅したことがあります。

## スクリーンショットは撮って置くだけ

autolog がやるのは、撮って置き場に保存するところまでです。
gkill へ入れるのは、既存の同期スクリプトと `gkill_server idf` の役目です。

gkill の IDF は**ファイルの更新時刻を記録時刻として使う**ので、
保存した直後に更新時刻を撮影時刻へ合わせます。これをしないと、
取り込んだ日時で記録されてしまいます。

置き場は日付で分けずフラットにします。`dvnf move` はディレクトリを渡すと
移動先に入れ子で作ってしまうため、ファイルを直接移動させる必要があります。

## Android は JSONL で受け渡す

収集アプリと `autolog` は別のアプリなので、互いのアプリ専用領域は見えません。
共有ストレージだけが接点です。

そこに **SQLite は置きません。** 共有ストレージは FUSE で、
複数のプロセスから開くとファイルロックが期待どおりに効かず、壊れます。

アプリは追記専用の JSONL を書き、`autolog` がそれを読んで自分の生ログへ入れます。
書きかけを読まれないよう、`.jsonl.tmp` に書いてから `.jsonl` へ名前を変えます。

## Android のバイナリはアプリに埋め込まない

gkill 本体の Android アプリは、サーバのバイナリを APK に同梱して実行します。
autolog は同じことをしていません。

gkill を Termux で動かしている場合、Termux には Go もバイナリを配る仕組みも既にあります。
同じ形で配れるなら、APK を大きくする理由がありません。

## Go は Android で時刻をずらす

Go は Android で `time.Local` を UTC に固定します
（標準ライブラリの `zoneinfo_android.go` がそう実装しています）。
`TZ` を設定しても変わりません。

生ログも gkill も時刻を文字列で持ち、その文字列で並べ替えます。
オフセットが混ざると、並び順が時刻順と一致しなくなります。
絶対時刻としては正しいのに、後から直すのが難しい壊れ方をします。

そのため Android では、システム設定からタイムゾーンを読んで
`time.Local` を自分で設定します。

## 端末名をコードに書かない

端末名・利用者名は設定で決めます。コードには既定値すら置きません。

端末利用の記録のタイトル（「Windows利用」など）も設定です。
呼び分けたい語は環境によって違うので、コードに埋め込むと他の人が使えません。
