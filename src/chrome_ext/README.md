# gkill autolog Chrome 拡張

閲覧したページと動画・音楽の再生を `autolog collect` へ送る MV3 拡張。

再生の計測は YouTube / YouTube Music に限らず、すべてのサイトで行う。
そのため読み込み時の権限表示は「すべてのサイトのデータの読み取りと変更」になる。

個人利用のため署名配布はせず、開発者モードで読み込む。

## 導入手順

1. `autolog collect` を一度起動して共有トークンを生成させる。
   トークンは `%LOCALAPPDATA%\gkill_autolog\ingest_token.txt` に作られる。
2. Chrome で `chrome://extensions` を開き、右上の「デベロッパー モード」をオンにする。
3. 「パッケージ化されていない拡張機能を読み込む」で、このディレクトリを選ぶ。
4. 拡張の「詳細」→「拡張機能のオプション」を開き、共有トークンを貼り付けて保存する。

送信先は既定で `http://127.0.0.1:19921/ingest`。
`AUTOLOG_INGEST_ADDR` を変えた場合はオプション画面の送信先も合わせる。

## 動作確認

1. 適当なページを 1 分ほど開いてからタブを切り替える。
2. `autolog status --since 1h --dump` に `browser_view` が出ることを確認する。
3. YouTube で動画を 1 分ほど再生し、別の動画へ移る。
4. `media_play` が出て、`played_seconds` が実際の再生時間に近いことを確認する。
5. YouTube で動画を 1 分ほど再生し、**手を触れずに自動再生で次の動画へ 2 回移らせる**。
   `media_play` が 3 件出て、各件の `video_id` と `title` が同じ動画のものに
   なっていることを確認する。ここがずれていたら、タイトルを報告時に読み直している。
6. YouTube Music で曲を再生したままライブラリへ移動し、そのまま数分聴く。
   曲ごとに `media_play` が出ることを確認する。
7. YouTube のホーム・検索結果でサムネイルにマウスを乗せてプレビューを流し、
   `media_play` が出ないことを確認する。
8. YouTube 以外の動画サイトでも 1 分ほど再生し、`service` が `web` の
   `media_play` が出ることを確認する。

送信できていないときはオプション画面の「未送信のイベント」が増える
（5000 件で頭打ちになり、以後は古いものから捨てられる）。
`autolog collect` が動いているか、トークンが一致しているかを確認する。
受け口に拒まれた不正なイベントが混ざっていた場合は、その1件だけを
自動で特定して捨て、残りの送信は止まらない。

## 記録するもの

| いつ | 内容 |
|---|---|
| タブが見えている間 | `browser_view`（URL・タイトル・タブID・ウィンドウID・表示開始/終了） |
| 動画・音楽の再生 | `media_play`（URL・タイトル・アーティスト・実再生秒数、YouTube 系は動画IDも） |

閲覧区間は「フォーカスされたウィンドウのアクティブタブ」である間だけ開く。
別タブや別アプリへ移った時点で閉じる。同じ URL を再度開いた場合は別の区間として扱う。

再生は `<video>` / `<audio>` を 1 秒ごとに見て数える。計測は再生が始まってから動かし、
対象が無くなったら止める（すべてのサイトに入るため、何もないページで走査し続けない）。
YouTube 系は動画ID（Shorts はパスから）、それ以外はページ URL を「同じ再生か」の判定に使う。
判定に使う値が変わったらそこで区切るので、**自動再生で次の動画・次の曲へ進んだ場合も
1 本ずつ別の `media_play` になる**。

動画IDは URL から取り、`?v=` が付いていなければ `navigator.mediaSession` の
サムネイル URL (`https://i.ytimg.com/vi/<動画ID>/...`) から確認する。
ミニプレイヤーでの再生と、YouTube Music でライブラリやホームを表示したままの
再生がこれに当たる。パスに入っているのは動画IDそのものなので推測ではない。

YouTube Music でどちらからも動画IDを取れないとき（アルバムアートが
`googleusercontent.com` の場合）は、曲名を「同じ再生か」の判定に使い、
URL を付けずに記録する。取り込み時の normalize がこれを TimeIs だけにする。
YouTube 本体で動画IDを取れないのはホーム・検索結果で、サムネイルのプレビューが
鳴っているだけのことがあるため何も数えない。

タイトルは `navigator.mediaSession` のメタデータを優先し、無ければページタイトルを使う。
**タイトルは計測している間に取り込み、報告時に画面から読み直さない。**
切り替わりに気づくのは切り替わった後なので、報告時に読むと直前の再生に
次の動画のタイトルが載ってしまう。

実再生秒数には一時停止時間と広告再生時間を含めない。シークで飛ばした分も数えない。
広告の判定は YouTube でのみ行える。

**広告で再生は分断しない。** YouTube は広告を同じ `<video>` 要素で再生し、
その間は要素の長さが広告のもの（30 秒未満が多い）になるため計測対象から
外れて見えるが、広告の表示中は同じ再生の続きとして待つ。
広告以外で対象が見えなくなった場合（SPA のプレイヤー差し替えなど）も
数秒だけ様子を見てから確定する。

## 記録しないもの

- URL を確定できなかった再生の URLog（検索URLや推測URLは作らない。
  何を再生したかは分かるので TimeIs としては残る）
- ループ再生の素材、長さが 30 秒未満と分かっている素材（装飾目的の自動再生とみなす）
- 消音での再生（YouTube 系を除く。一般のサイトでは装飾目的の目印になるため）
- iframe の中で再生されているもの（親ページの URL を確認できないため）
- プレイリストやアルバムのパラメータ（YouTube 系は正式な `watch?v=` 形式だけを保存する）

30 秒未満の閲覧・再生を落とす判定や、不要ページの除外は
この拡張ではなく取り込み時の normalize と `url_denylist.txt` が行う。
判定基準を1か所に集めるため、拡張側では絞り込まない。

## 実装メモ

MV3 の Service Worker はいつでも停止されるため、状態とキューはすべて
`chrome.storage.local` に置いてある。

- 閲覧区間は 30 秒ごとの心拍で更新する。心拍が 90 秒以上途切れていた場合、
  Service Worker が止まっていたとみなし、終了時刻に現在時刻ではなく最後の心拍時刻を使う。
- 再生は 10 秒ごとに途中経過を Service Worker へ報告する。
  タブが突然閉じられて最後の報告が届かなくても、直前までの実績は残る。
  報告は `playId` ごとに上書きするので、**最後の報告の内容が確定値になる**。
  そのため報告に載せる値は、報告の時点ではなく計測中に確定させておく必要がある。
- **一度確定した再生が続いた場合、続きは差分の区間として記録する。**
  スリープ復帰などで報告が途絶えると心拍がそこまでを確定させるが、
  ページ側は生きていて累計の実再生秒数のまま報告を再開することがある。
  確定した時点の累計を墓標 (`finalizedPlays`) に残し、以後の報告は
  「累計 − 確定済み」の差分に組み替える。二重計上とイベントの重複を防ぐ。
  ページを離れるとき (`pagehide`) は content script 側が play を捨て、
  bfcache から復元された再生は新しい `playId` で数え直す。
- 送信に成功した分だけキューから外すので、`autolog collect` が止まっていても失われない。
- **`chrome.storage` を触る処理は Promise チェーンで直列化してある。**
  get → 変更 → set は原子的でなく、タブを閉じたときは閲覧の確定と再生の確定が
  ほぼ同時に走るため、直列化しないと後勝ちで片方のイベントが黙って消える。
  状態を触る関数はロックを取らず、入口（イベントリスナ）だけで取る決まり。
  例外は `removeFromQueue` で、ロックの外で走る送信 (`flush`) から呼ばれるため自分で取る。

## テスト

```
npm run test_chrome_ext
```

Node の標準テストランナーで `background.test.mjs` を動かす。
chrome API は `chrome.storage` の非同期性だけを再現したスタブで、
並行イベントでキューが消えないことなどを検証している。
